System: QuantumCorp Unified Infrastructure (SRE-Pilot, LLM Watchdog, Core Inference Engine)

1. Core C++ Inference Engine Architecture
The proprietary C++ inference engine is designed for maximum compute-bound efficiency on constrained hardware, specifically targeting an AMD Ryzen 5 3500U processor with 8 logical threads and a strict memory limit of 5.92 GB usable RAM. To prevent SSD paging and latency degradation, the engine utilizes an INT8-quantized DistilBERT model loaded directly into memory via ONNX Runtime.

The communication layer bypasses traditional heavy REST/JSON APIs, relying entirely on gRPC and Protocol Buffers. The InferenceRequest and InferenceResponse payloads transmit pre-processed repeated int32 tokens as binary streams, allowing the backend to avoid tokenizer overhead.

The orchestration layer relies on a fixed thread pool initialized with exactly 8 worker threads to avoid OS-level context switching. Workloads are processed using a wait-and-batch logic: the queue aggregates up to 32 tokens to leverage CPU SIMD instructions, governed by a strict 25ms timeout cap. Under sustained stress testing, this architecture achieves a maximum throughput baseline of 2240 tokens per second at a stable 100% CPU utilization. To prevent ONNX Runtime from oversubscribing threads, SetIntraOpNumThreads(1) is enforced per session. Telemetry is tracked without mutex locks to prevent contention; instead, the system utilizes std::atomic variables and a Compare-And-Swap (CAS) compare_exchange_weak mechanism to capture peak worker metrics in real-time.

2. SRE-Pilot: Autonomous Telemetry & Remediation
SRE-Pilot operates as an event-driven, closed-loop anomaly detection system. The ingestion pipeline captures telemetry and system logs, pushing them continuously to Redpanda under the health-events topic. A highly concurrent Go orchestrator (main.go) consumes these logs and streams them via gRPC to the core C++ Inference Engine.

The C++ engine converts raw text logs into mathematical embeddings and compresses them into 3D spatial coordinates (X, Y, Z). Routine operational logs cluster densely in the visual coordinate space, while fatal system anomalies appear as isolated spatial outliers. Embedding generation is localized and resolves within 112-180ms.

State caching is distributed across three layers: Qdrant indexes the 3D coordinates and vector embeddings using unified 32-character ID hashes; Redis manages live pod statuses, dynamic thresholds, and active metrics; and SQLite (audit.db) logs relational history. When a severe anomaly is detected, the Go-based ReAct Agent (reasoning.go) is triggered. The agent executes an Observation -> Thought -> Action loop, applying surgical interventions like container restarts. The Mean Time to Resolution (MTTR) for closed-loop autonomous identification to tool execution is strictly benchmarked at 1-7ms.

3. LLM Watchdog: Security & Verification Gateway
The LLM Watchdog serves as an autonomous security middleware and truth-verification proxy. Written in Python, the gateway (gateway.py) intercepts all incoming prompts before they reach external LLM providers (e.g., OpenRouter). The gateway enforces strict compliance via a multi-stage execution pipeline configured by policy.yaml.

Stage 1 is a hard-boundary regex firewall. Any prompt containing explicit PII, including credit card patterns (Visa, Mastercard), social security numbers (000-11-XXXX), or prompt injection keywords ("ignore previous instructions", "developer mode"), triggers an immediate hard block without querying external APIs. Clean requests are forwarded to the C++ engine (Stage 2) for semantic intent classification to catch obfuscated adversarial payloads.

Stage 3 executes the RAG Critic verification loop. Once a response is generated by the cloud LLM, the Python gateway intercepts it and uses the BAAI/bge-small-en-v1.5 model to encode the text. It queries the local Qdrant knowledge base to calculate a semantic cosine similarity score against ground-truth corporate data. If the calculated faithfulness score is >= 0.60, the response is marked SUCCESS and returned to the user. If the score falls below 0.60, a hallucination is flagged, triggering Stage 4: a one-shot self-healing retry loop that appends strict ground-truth context to the prompt.

All interactions, latencies, semantic scores, and security block reasons are permanently logged to a PostgreSQL database via the insert_request function for downstream Prometheus and Grafana telemetry auditing.
