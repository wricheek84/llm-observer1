gRPC Protocol Architecture & HTTP/2 Transport Specification
1. Wire Protocol Framing and Stream Sequence Architecture
The gRPC protocol implements remote procedure calls by mapping message execution streams directly over HTTP/2 transport framing. A standard gRPC interaction consists of an isolated request and response sequence handled via a shared HTTP/2 stream identifier. The stream identification allows a single process to handle multiple independent requests concurrently over a single open TCP connection.

The general sequence of messages in a request pipeline begins with Request-Headers, followed by zero or more Length-Prefixed-Messages, and terminates with an End-of-Stream (EOS) signal. Request-Headers are delivered as HTTP/2 header blocks across HEADERS and CONTINUATION frames. The protocol mandates that the HTTP/2 method must always be a POST command, the scheme must be http or https, and the path must follow a strict case-sensitive format structured as /:serviceName/:methodName. Implementations strongly discourage overriding this path structure, as doing so breaks service configuration compatibility. If the incoming content-type header does not explicitly begin with application/grpc, the server must reject the request immediately with an HTTP Status 415 (Unsupported Media Type) to prevent standard web browsers or incompatible HTTP/2 proxies from misinterpreting a failed gRPC stream.

2. Length-Prefixed Messages and Data Framing Data Plane
The actual payload data transmitted during an RPC call is packed into a sequential series of Length-Prefixed-Message items delivered entirely inside HTTP/2 DATA frames. It is a critical transport rule that HTTP/2 DATA frame boundaries have no direct structural relation to gRPC Length-Prefixed-Message boundaries; downstream parsing layers must make no assumptions about their alignment.

A standard Length-Prefixed-Message is composed of a 1-byte unsigned integer Compressed-Flag, a 4-byte big-endian unsigned integer Message-Length, and the raw binary octet sequence of the Message itself. A Compressed-Flag value of 1 indicates that the message bytes are compressed using the compression algorithm declared globally by the grpc-encoding header (such as gzip, deflate, or snappy). A flag value of 0 indicates the payload bytes are uncompressed. Compression contexts are strictly isolated and are never maintained across message boundaries; gRPC implementations must instantiate a completely new compression context for every individual message in the stream. For incoming requests, the End-of-Stream (EOS) boundary is explicitly signaled by the presence of the END_STREAM flag on the final received DATA frame. If the request stream must be closed but no payload bytes remain to be sent, the client runtime must transmit an empty DATA frame carrying this flag.

3. Response Lifecycle, Status Codes, and Trailers
A gRPC response sequence delivers metadata, payload messages, and termination status back to the client using either a combination of Response-Headers, Length-Prefixed-Messages, and Trailers, or a condensed Trailers-Only block if an immediate application error occurs. Response-Headers and Trailers-Only blocks are each packed into a single HTTP/2 HEADERS frame block. Most successful responses return a standard HTTP Status 200 header block alongside the application's specific content type.

The definitive completion of an RPC call is governed by the Trailers block. gRPC requires that the definitive status code must always be sent in the Trailers frame, even if the status is a successful OK (Status 0). The trailers contain a decimal-encoded ASCII grpc-status integer and an optional percent-encoded UTF-8 grpc-message string describing any runtime errors. If an application error occurs, an additional grpc-status-details-bin binary header may be appended to transmit a base64-encoded protobuf message detailing the error context. Servers and clients suggest a default size limit of 8 KiB each for headers and trailers to prevent memory exhaustion. The final termination of a response stream is declared by the presence of the END_STREAM flag on the HTTP/2 HEADERS frame carrying the final Trailers metadata.

4. Service Method Classifications and Lifecycle Execution
Through its Interface Definition Language (IDL)—typically implemented using Protocol Buffers—gRPC allows developers to declare four distinct kinds of remote method invocation patterns. Unary RPCs model a standard function call where the client emits a single structured request and blocks or waits to receive a single response back. Server-Streaming RPCs accept a single request from a client but reply with a continuous stream of multiple sequentially ordered messages; the stream completes only when the server transmits its final status details and trailing metadata.

Conversely, Client-Streaming RPCs allow a client to open a stream and transmit a continuous sequence of multiple request messages sequentially; the server processes the incoming data stream and returns a single unified response block once the client signals execution is finished. Finally, Bidirectional Streaming RPCs allow both the client and server to read and write messages concurrently using independent, decoupled read-write streams. Because the two streams operate entirely independently, the application logic can dictate any interleaving pattern, such as full ping-pong synchronization or completely asynchronous reading and writing, while the transport layer strictly preserves the message ordering within each isolated direction.

5. Deadlines, Application Metadata Boundaries, and Channel States
Every gRPC interaction is bounded by a deadline or timeout mechanism. Clients can pass a grpc-timeout header containing a positive integer and a time unit (ranging from hours down to nanoseconds) to specify how long they are willing to wait for a response before the call is terminated locally with a DEADLINE_EXCEEDED error. If omitted, the server assumes an infinite timeout baseline. Both clients and servers evaluate success independently and locally; an RPC can complete successfully on a server's local state machine but still flag a failure on the client side if the trailing frames arrive after the specified deadline has expired. Either side can explicitly trigger an RPC cancellation at any point, terminating active computation immediately without rolling back any mid-flight data updates.

Custom application data is passed across the network using Metadata key-value lists. Keys are strictly case-insensitive ASCII strings composed of alphanumeric characters, hyphens, underscores, and periods, and must never begin with the reserved grpc- prefix. Binary metadata keys must utilize a -bin suffix, instructing the underlying runtime library to automatically apply base64 encoding before transmission and decode it upon receipt. These operations are managed by a gRPC Channel, which maintains the physical connection abstraction to the remote host and port, tracking internal lifecycle states such as connected, idle, or transient failure.

6. Connection Management, GOAWAY Signaling, and PING Layer Telemetry
Long-lived gRPC connections are governed by explicit HTTP/2 kernel framing signals to handle clean teardowns, load balancing, and connection liveness checks. A server signals that it is preparing to shut down or terminate a connection by broadcasting a GOAWAY frame. This frame transmits the internal identifier of the last successfully processed stream. Clients must interpret any stream initiated after this boundary as UNAVAILABLE and automatically route or retry those calls elsewhere, while safely allowing already accepted streams to run to completion before terminating the physical TCP socket.

To verify path viability and estimate network round-trip performance, both clients and servers can transmit PING frames, which the receiving peer must immediately echo back bit-for-bit. If a server-initiated PING deadline expires without a response, all outstanding calls on that channel are closed with a CANCELLED status. If a client-initiated PING times out, its open calls are aborted with an UNAVAILABLE status. If a radical framing error or connection drop occurs, the runtime transmits an RST_STREAM frame to force full closure. The gRPC architecture translates these low-level transport errors directly into standardized gRPC status codes: a REFUSED_STREAM maps directly to UNAVAILABLE (allowing safe retries), an ENHANCE_YOUR_CALM code maps to RESOURCE_EXHAUSTED (indicating bandwidth exhaustion), and an INADEQUATE_SECURITY signal maps to PERMISSION_DENIED to indicate that the underlying TLS layer violates protocol constraints.
